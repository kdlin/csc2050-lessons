The Filing Cabinet

List a folder, turn names into paths, tell files from folders, and walk an entire directory tree with recursion.

~35 min · 14 checkpoints · Lab 7 topic

The new job P can clone itself (Ch 1), share a whiteboard (Ch 2), and keep the clones from fighting over it (Ch 3). Now P gets a new kind of job: go into a folder and count everything inside, including the folders inside the folders. That takes three skills: list a folder (5.1), turn a name into a path (5.2), tell a file from a folder (5.3). Then recursion ties them together (5.4). 
#include <stdio.h>
#include <string.h>
#include <dirent.h>    // opendir readdir
#include <sys/stat.h>  // stat lstat S_ISDIR

5.1A directory is a list of names

Analogy: a folder in a filing cabinet has a table of contents taped inside the cover. Opening the folder doesn't hand you the documents, just that list of names, one line at a time.

That's literally what a Unix directory is: a special file holding names. In Eckhardt's words, "they're just names, they're just character arrays."

DIR *d = opendir(path);  // NULL = failed
struct dirent *entry;
while ((entry = readdir(d)) != NULL) {
    printf("%s\n", entry->d_name);
}
closedir(d);
CallLikeReturns

Eckhardt: readdir "will read one entry at a time... it's like fread, it goes further on automatically, and when it's at the end it will return null." In while ((entry = readdir(d)) != NULL), the inner parentheses assign first, then compare.

The two strange entries

.    this directory     ls .   = here
..   the parent         cd ..  = go up

Every directory lists them, every time. He points them out in his demo: "the single dot represents itself... the double dot represents the parent directory."

Skip them When you walk into subfolders, entering . puts you back in the same folder and .. goes up, so you loop forever. Every walker starts with:
if (strcmp(name, ".") == 0 || strcmp(name, "..") == 0) continue;
strcmp returns 0 when the strings are equal. Never compare strings with ==, which only compares the pointer addresses.

5.2A name is not a path

readdir gives you "notes.txt", just the name, not where it lives.

opened:  /home/kdlin/2050
d_name:  "notes.txt"
real:    /home/kdlin/2050/notes.txt

A bare name is looked up relative to the program's current working directory, the folder you launched it from. Eckhardt gets burned by this on camera: his stat returned -1 and garbage numbers because VS Code's debugger started the program from a different folder than the code runner.

The fix: glue the folder and the name together.

char full[1000];
snprintf(full, sizeof(full), "%s/%s",
         path, entry->d_name);
// "/home/kdlin/2050" + "notes.txt"
// -> "/home/kdlin/2050/notes.txt"

snprintf is printf into a string, and the n means it never writes past sizeof(full). A very long path gets cut off instead of overflowing the buffer. He uses 1000 characters as a safe path size.

5.3File or folder? stat

Names don't say what they are: notes could be a file or a folder. Analogy: reading the table of contents gives you labels. stat walks to the drawer and pulls the index card: type, size, timestamps.

struct stat st;
if (stat(full, &st) == 0) {     // 0 = ok
    if (S_ISDIR(st.st_mode))
        printf("dir\n");
    else if (S_ISREG(st.st_mode))
        printf("file, %ld bytes\n",
               (long)st.st_size);
} else {
    printf("stat failed\n"); // -1
}
  • The struct and the function are both called stat. "The weird thing here is that the structure is called stat but the function is also called stat."
  • &st: you pass the address because the struct is an output that stat fills in. "It's not an input, it's an output."
  • Return value: 0 means success, -1 means error. On -1 the struct is garbage, which is exactly what bit him in the debugger. Always check it.
  • st_mode packs the type bits. Decode it with macros: S_ISDIR (folder), S_ISREG (regular file), S_ISLNK (symlink, visible only with lstat).

Other fields he shows: st_size (bytes), st_blksize (usually 4K: even a 3-byte file takes a 4K block on disk, the same idea as memory pages), and the access, modify and change timestamps.

stat vs lstat

A symbolic link is a shortcut: a tiny file pointing at another path.

stat(link)   follows it, describes TARGET
lstat(link)  describes the LINK itself

A shortcut inside a folder can point back up at that folder. A walker using stat sees "directory!", walks in, finds the shortcut again, and keeps going forever. lstat reports "this is a link", so you count it and move on. Same call, same struct, one letter different.

5.4Walking the whole tree

Eckhardt leaves this as a puzzle at the end of his Directories video. You could nest a second opendir loop, then a third... "that's not a smart way. Smart would be if you take this into a function and do it recursively."

Analogy: your instructions for inventorying any folder: "For each item: if it's a document, tally it. If it's a folder, follow these same instructions on it, then come back and keep going."

void walk(const char *path) {
    DIR *d = opendir(path);
    if (!d) return;
    struct dirent *e;
    char full[1000];
    while ((e = readdir(d)) != NULL) {
        if (!strcmp(e->d_name, ".") ||
            !strcmp(e->d_name, ".."))
            continue;               // 5.1
        snprintf(full, sizeof full,
                 "%s/%s", path, e->d_name); // 5.2
        struct stat st;
        if (lstat(full, &st)) continue; // 5.3
        if (S_ISDIR(st.st_mode)) {
            dirs++;
            walk(full);              // 5.4
        } else {
            files++;
        }
    }
    closedir(d);
}

!strcmp(a, b) is shorthand for strcmp(a, b) == 0. if (lstat(...)) is true when it returns -1, meaning it failed.

2050/
├── a.c
├── pics/
│   ├── cat.bmp
│   └── old/
│       └── dog.bmp
└── b.c

walk("2050")
 a.c      files=1
 pics     dirs=1 -> walk("2050/pics")
   cat.bmp  files=2      (2050 paused)
   old      dirs=2 -> walk(".../old")
     dog.bmp files=3
     closedir, return
   closedir, return
 b.c      files=4    (2050 resumes)

Why it works

1.Every call has its own d, e and full on the stack. While walk("2050/pics") runs, the outer loop is frozen with its own DIR * still holding its place.
2.The base case is built in: a folder with no subfolders makes no recursive call, so the loop ends, closedir runs, and it returns.
3.Skipping ./.. and using lstat keep it finite. Without them it recurses forever.
files = 4, dirs = 2 (the root itself isn't counted)
Chapter 3 connection If two processes each walk part of the tree and bump the same counters, those counters live in mmap shared memory and every dirs++ / files++ is a critical section. That's where Peterson comes back.
