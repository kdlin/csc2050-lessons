Two Clones, One Marker

Why shared memory breaks counters, what a mutex has to guarantee, and how Peterson's algorithm guarantees it with two variables.

~45 min · 18 checkpoints · Lab 7 topic

Previously Ch 1: P cloned itself with fork(). Every clone gets a private copy of memory.
Ch 2: private copies can't share work, so P put up a whiteboard: mmap(MAP_SHARED | MAP_ANONYMOUS), created before the fork, visible to both clones.

Then P gave both clones one job: count to 2,000,000 together, 1,000,000 each, on one shared tally. The board said 1,147,382.

3.1The crash: race conditions

count++ looks like one action. The CPU does it in three:

LOAD   count -> register   read the board
ADD    register + 1        math in your head
STORE  register -> count   write the board

The scheduler can switch processes between any two of those steps. On a multicore machine the clones don't even take turns: they run at the same instant.

 Parent       Child        board
 LOAD (5)                    5
              LOAD (5)       5  <- switch
 ADD -> 6                    5
              ADD -> 6       5
 STORE 6                     6
              STORE 6        6  <- 2 counts,
                                  board +1
Definition Race condition: the result depends on the timing of the processes, not on the code. Same program, different answer every run.

Eckhardt's demo ("Mutex part 1"): a child keeps overwriting a shared buffer with two quotes while the parent prints it. The output was pieces of both quotes glued together. "Totally messed up, and that's a race condition." Your own race.c printed 1,350,684, then 1,199,468, then 1,027,896. Never 2,000,000.

3.2Critical section + what a mutex must guarantee

The critical section is the code that touches the shared data. A mutex (mutual exclusion) is the guard on its door. Both processes wrap it the same way:

for (i = 0; i < 1000000; i++) {
    lock(me);      // wait for permission
    (*count)++;    // critical section
    unlock(me);    // give it back
}

me is 0 for one process and 1 for the other, and other is 1 - me. Every variable the lock uses lives in mmap shared memory. Otherwise each process checks its own private copy.

In "Mutex part 2", Eckhardt says a good mutex gives you three things:

#RequirementPlain English
1Mutual exclusionAt most one process inside at a time
2No deadlockThey never both wait forever
3No lockoutNobody is shut out while the other isn't even trying

The next three sections are three tempting designs. Each one fails exactly one requirement. Once you see why, Peterson makes sense.

3.3Attempt 1: the OCCUPIED sign

Analogy: a single-stall bathroom with a sign you flip yourself. If it says OCCUPIED, wait. If it says FREE, flip it and go in. Flip it back on the way out.

void lock() {
    while (*busy == 1)  // OCCUPIED?
        ;               // stand and re-check
    *busy = 1;          // flip, walk in
}
void unlock() { *busy = 0; }

The lone ; is an empty loop body: the process does nothing but re-check the sign, over and over. That's busy waiting (spinning).

The normal case works. P0 sees FREE, flips it, enters. P1 arrives, sees OCCUPIED, spins. P0 leaves and flips it to FREE. P1's next check sees FREE and it enters.

The failure. Checking and flipping are two separate steps:

busy=0  P0: sees FREE, about to flip
            <- switch to P1
busy=0  P1: sees FREE (P0 hasn't flipped)
        P1: busy=1, walks in
            <- switch to P0
busy=1  P0: resumes at "flip": busy=1, in
        BOTH INSIDE

P0 already looked. When it resumes, its next instruction is the flip, not the check, so it never looks again.

The disease Read, then act, with a gap in between. That's the same bug as count++. The lock has the very race it was supposed to prevent. If the check and the flip ran as one unbreakable (atomic) step, this would work. Plain C assignments aren't atomic.

3.4Attempt 2: strict turns

Analogy: a talking stick. Only whoever holds the stick may speak, and when you're done you hand it to the other person.

// shared: int *turn, starts at 0
void lock(int me) {
    while (*turn != me)  // not mine?
        ;                // spin
}
void unlock(int me) {
    *turn = 1 - me;      // hand it over
}

Mutual exclusion holds: turn is one value at a time, so only one process can match it. Nobody grabs anything. You wait to be handed the turn, so there's no gap.

The failure: lockout. The processes are forced into strict P0, P1, P0, P1 order:

turn=0  P0: in, count++, turn=1
turn=1  P0: wants in again -> spins
        P1: busy elsewhere, or
            already finished and exited
turn=1  P0: spins forever.
        The room is EMPTY.

Eckhardt traces this on the whiteboard: the scheduler swaps at the wrong moment and the other process is "locked out... no chance." The stick ends up in the hand of someone who doesn't want to talk.

3.5Attempt 3: raise your hand

Analogy: in a meeting, raise your hand when you want to speak, and wait while the other person's hand is up.

// shared: int flag[2] = {0, 0}
void lock(int me) {
    flag[me] = 1;          // I want in
    while (flag[1 - me])  // you too?
        ;                  // wait
}
void unlock(int me) { flag[me] = 0; }

This fixes Attempt 2: you only wait if the other actually wants in. If P1 is off doing something else, its hand is down and P0 walks right in.

The failure: deadlock.

P0: flag[0] = 1       hand up
P1: flag[1] = 1       hand up
P0: waits for flag[1] to drop
P1: waits for flag[0] to drop
    both polite, stuck forever

Two people at a doorway, both saying "no, you first," forever.

3.6Peterson's algorithm

MutexNo deadlockNo lockout
1. Sign✗✓✓
2. Turns✓✓✗
3. Hands✓✗✓

Attempt 3 has the intent (hands). Attempt 2 has the tiebreaker (turn). Peterson uses both.

// shared (mmap): flag[2] = {0,0}; turn;
void lock(int me) {
    int other = 1 - me;
    flag[me] = 1;      // 1. hand up
    turn = other;      // 2. "after you"
    while (flag[other] && turn == other)
        ;              // 3. wait only if you
                       //    want in AND it's
                       //    your turn
}
void unlock(int me) { flag[me] = 0; }
The doorway Two people reach a narrow doorway together. Each raises a hand ("I'd like to go") and says "after you." If both say it, whoever said it last waits, because theirs is the "after you" still standing. The other walks through.

while (flag[other] && turn == other) means wait while you want in AND it's your turn. So I go ahead if either:

  • flag[other] == 0: you don't want in. Go. (kills lockout)
  • turn == me: you said "after you" after me. Go. (breaks the tie)

Why all three hold

1.Mutual exclusion. If both were inside, both hands are up, so each got past only because turn pointed at itself. P0 needed turn==0 and P1 needed turn==1. turn can't be both.
2.No deadlock. Both waiting needs turn==1 and turn==0 at the same time. Impossible.
3.No lockout. If P1 isn't trying, flag[1]==0 and P0 walks in. If P1 leaves and races back, it sets turn=0, which hands priority to P0. It can't cut in line twice.
The last one to yield is the one that waits.
The tie, traced:
P0: flag[0]=1
P1: flag[1]=1
P0: turn=1        "after you"
P1: turn=0        "no, after YOU" (last)
P0: flag[1] && turn==1 ? no  -> ENTERS
P1: flag[0] && turn==0 ? yes -> waits
P0: unlock, flag[0]=0
P1: flag[0] ? no             -> ENTERS

Eckhardt's names vs these names

He builds it on the whiteboard in "Mutex part 2" with different names. It's the same algorithm:

LectureHereMeaning
flag ("in favor of the other")turntiebreaker
c1, c2 ("attempt to enter")flag[0], flag[1]raised hands

His story matches this one: a single "favor" variable gives a mutex but can lock someone out, and adding the "attempt" flags fixes it.

3.7Why Peterson still miscounts on real CPUs

Peterson is provably correct on paper. On a modern multicore machine it can still lose a few counts: in testing, plain Peterson was exact in about half the runs and short by 1 to 5 in the rest. Two reasons, both from Piazza posts the instructor endorsed:

1. Store buffers (the hardware)

Each core has a small store buffer. Writes go there first and reach shared memory a moment later.

Core 0               Core 1
flag[0]=1            reads flag[0]
 -> [store buffer]    from memory: 0!
   (not visible yet)  -> thinks P0 is
                        not trying -> IN

Analogy: you raise your hand, but it's behind frosted glass for a split second. The other person looks, sees no hand, and walks in. Peterson's proof assumes writes are visible to the other side immediately, and the hardware breaks that.

2. The compiler keeps values in registers

To go fast, the compiler may read flag[other] once into a register and spin on that stale copy forever. That's why class code is compiled without optimization (-O0).

Real-world fixWhat it does
memory fenceflushes the store buffer before continuing
volatiletells the compiler: re-read memory every time
library mutex (pthread_mutex_lock)the OS and hardware handle it correctly
Class scope You won't write any of these for class. Know why it can fail, in one sentence: "a write sitting in one core's store buffer isn't visible to the other core yet, so both see the other's flag as 0 and both enter."

3.8Costs and design

Busy waiting burns CPU. A spinning process re-checks the flag millions of times per second and does nothing useful. Real mutexes put the waiter to sleep and wake it when the lock frees up.

Granularity: how much code goes inside the lock?

FINE: lock; count++; unlock;  x1,000,000
  + processes interleave (parallel)
  - millions of lock/unlock calls

COARSE: lock; entire loop; unlock;
  + one lock call
  - the other waits the WHOLE time
    = no parallelism. Why fork at all?
Senior move Count locally in a plain non-shared int, then lock once at the end to add your total to the shared counter. You get full parallelism and almost no locking. Keep it in your back pocket; class asks for the simple version.
